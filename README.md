# CS360-SNHU

The Inventory App is designed for anyone looking to keep track of items in a easily, all in one place. This can be used in a workplace setting, or for personal use. 
To enable this functionality, the app allows the user to create a log in and password, and then log in to that account and add items to their inventory. After adding items to their inventory, the user can edit the amount of any given item they have in inventory, or delete it entirely.

The UI was designed with the4 end user in mind. The colors are consistent throughout the app, and the top banner stays the same through multiple screens. The app opens to the log in screen, which can then be used to log in or create a new user. The log in screen also includes toasts as feedback when the user attempts to log in and it fails, or when they attempt to create a user which already exists. The user is then taken to the Inventory screen after logging in is completed, where they then can add items by using the floating action button and then filling out a pop-up form for the item. My designs made the user experience simple and easy, as well as consistent and clear to understand. My designs also utilized the Android reccommended button placement themes, via the floating action button in the bottom right hand corner, making the app operate in a familiar manner to other android applications.

Writing the code for the app was quite difficult, as I wanted to preserve an object oriented hierarchy while also making the code as simple as possible. I created two main objects for the application, Users and Items. Items populate the Inventory Table, and Users hold log in information, as well as a linked list of Item objects for populating that specific user's table. Saving was achieved by creating a linked list of users on the apps saved preferences, which is static and saved via serialization through JSON/GSON. After these basic structures were created, the rest was simply input validation and tranposing user input into the functions needed to save and apply the data to the screens. The inventory table itself was particularly difficult to create, as formatting it was a bit difficult, and makes up the bulk of the code for the inventory screen, as it must be dynamically created each time an item is edited, removed or added. In the future, I may choose to use a more complex framework for the inventory table, which enables editing without rebuilding the entire table. 
I was able to take this approach by working backwards. I started with the main functions the app needed to possess, and asked myself what needed to be present in the program's code for that function to come to life on screen. I then followed each rabbit hole until I came to the two basic objects of Users and Items. I then realized I'd need a static class to manage the users between app uses, and created a User Manager class which handled the basic saving functions and input validation functions. I then created the rest of the functions from there for receiving input from the UI and trasposing it into directions the program can follow to provide the desired functionality to the user. I will definitely use this development philosophy in the future when creating complex applications.

Testing was very important to the development of this project. This app was made with the end user in mind through every step of development. Each time I added a new feature, I tested the program to make sure it worked as intended, as well as to bring to light any unintended consequences of the new feature. For instance, when testing the pop-up for adding an item, I realized there was no way to return to the inventory screen unless a new item was added. Therefore, I added an 'x' button to the pop-up that allows the user to exit the add item screen if they deciede after clicking to add an item, that they no longer want to.

Development was the most difficult stage of this project. I quickly realized the design I had created in previous modules was simply out of the scope of what would be possible for me to create under any modest timeframe. Therefore, I made changes to the design which would shorten the development time without compromising any features or functionality which the end user needs. In the future, it will be important for me to be reserved in app functionality within the design phase, and add features in the development phase if I see them as needed. This is a much better workflow than trying to figure out what can be cut during development.

I am extremely happy with the results of the project, and particularly the saving aspect of the app. The app can be logged into with any amount of users, and save any amount of data between users. The app could even be used by the same person, under different users to separate different inventories. This feature combines my new found knowledge of using static objects and saving functions within the Android framework, with the object oriented knowledge I have gained from other coding courses.
